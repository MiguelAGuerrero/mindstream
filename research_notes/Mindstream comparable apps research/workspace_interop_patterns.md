## 1. Host-plus-tools products: how independently written tools declare capabilities and act on each other's content

### Takeaway
The dominant, proven pattern is "declare statically, activate lazily, invoke by command id": tools publish a declarative manifest (commands, menu placements, accepted types) that the host reads without running the tool, and the host builds all shared UI (palette, context menus, launcher) from that registry. Tools almost never call each other directly; they call a named command or raise a typed intent, which matches Mindstream's registry-plus-broker decision.

### Cited Findings
- VS Code: the host sets "context keys" reflecting UI state, and extensions use `when` clauses over those keys to enable or disable commands, menus and views; clauses support `!`, `&&`, `||` (example `textInputFocus && !editorReadonly`) — [VS Code when clause contexts](https://code.visualstudio.com/api/references/when-clause-contexts)
- VS Code: a command's palette visibility is controlled separately through a `menus.commandPalette` contribution taking the command id plus a `when` clause; command-level `enablement` applies to all menus and keybindings, whereas a menu item's `when` applies only to that one menu — [VS Code command guide](https://code.visualstudio.com/api/extension-guides/command)
- VS Code: invoking a command (keybinding or palette) emits activation event `onCommand:${command}`, so the extension is only loaded when first needed; before version 1.74.0 authors had to declare `onCommand` by hand for every user-facing command, after which the host derives it from the contribution — [VS Code command guide](https://code.visualstudio.com/api/extension-guides/command)
- VS Code UX guidance says the grouping of context menu entries should stay consistent across extensions — [VS Code context menu guidelines](https://code.visualstudio.com/api/ux-guidelines/context-menus.md)
- JupyterLab: plugin state is restored by executing commands; `ILayoutRestorer.restore` takes a widget tracker plus a command, an args function returning JSON arguments per widget, and a name; the restore command must return a promise that resolves only after the widget is created and added to the tracker — [JupyterLab LayoutRestorer API](https://jupyterlab.readthedocs.io/en/4.4.x/api/classes/application.LayoutRestorer-1.html), [ILayoutRestorer interface](https://jupyterlab.readthedocs.io/en/4.4.x/api/interfaces/application.ILayoutRestorer.html)
- FDC3 (the standard Mindstream drew on): apps register the intents they handle by "providing `interop.intents.listensFor` metadata in their AppD record"; registration in the app directory is the typical route but agents may also support dynamic registration at runtime — [FDC3 2.2 API spec (GitHub source)](https://raw.githubusercontent.com/finos/FDC3/main/website/versioned_docs/version-2.2/api/spec.md)
- Obsidian: core has only a basic `obsidian://` URI; the community "Advanced URI" plugin (scheme `obsidian://adv-uri`, formerly `obsidian://advanced-uri` before 1.44.0) was originally built to load workspaces by URI and can run any command by its palette name or internal id (example `commandid=workspace:close`); it ships a "Copy Command URI" command that generates a correctly encoded URI — [Advanced URI docs](https://publish.obsidian.md/advanced-uri-doc/Home), [Advanced URI commands](https://publish.obsidian.md/advanced-uri-doc/Actions/Commands)
- Obsidian x-callback returns are not in core either; the "Actions URI" community plugin builds a callback URL from `x-success` or `x-error` — [Actions URI callbacks](https://czottmann.github.io/obsidian-actions-uri/callbacks/)
- Obsidian plugin API churn: the API changelog lists outright removals (`prepareQuery`, `fuzzySearch`, `PreparedQuery`) and states that `getAbstractFileByPath` "has long been a point of confusion with plugin developers", fixed by adding file-specific and folder-specific lookups — [Obsidian API changelog](https://unpkg.com/obsidian@1.13.1/CHANGELOG.md)
- Obsidian user complaint: after updating to 1.7.4 with 64 plugins, a user argued that plugin developers cannot solely be blamed when plugins break and asked for backward compatibility and beta builds for plugin authors — [Obsidian forum thread](https://forum.obsidian.md/t/problems-updating-to-version-1-7-4-with-64-plugins/90675/9)
- Raycast: every item exposes an Action Panel; the first action is the primary action (runs on Return without opening the panel), the second is secondary (Cmd+Return); Cmd+K opens the full panel; sections group related actions (for example all copy actions); searching inside the panel flattens sections into one list; destructive actions render in red — [Raycast ActionPanel API](https://developers.raycast.com/api-reference/user-interface/action-panel), [Raycast manual: Action Panel](https://manual.raycast.com/action-panel)
- Apple App Intents: an intent's `perform()` returns `some IntentResult`, composed from protocols such as `ReturnsValue<T>` ("delivers a value back to the initiator"), `OpensAppIntent`, `ProvidesDialog` and `ShowsSnippetView`; the value type must be concrete — [Apple ReturnsValue docs](https://developer.apple.com/documentation/appintents/returnsvalue.md), [Apple developer forum](https://developer.apple.com/forums/thread/742278)
- Capacities publishes an x-callback-url interface and appends an error code and message to the `x-error` URL — [Capacities x-callback docs](https://docs.capacities.io/developer/x-callback-urls)
- Logseq: the DB version's April 2026 changelog "refactors plugin libraries to support the new sidebar integration path and newer DB-graph APIs", meaning plugin authors are mid-migration between two storage models — [Logseq DB changelog](https://discuss.logseq.com/t/logseq-db-changelog/30013/36)

### Inferences
- The single most transferable mechanic is VS Code's split between (a) a static declaration the shell can read without loading the tool, (b) a `when` expression over shell-owned context keys, and (c) a separate "show in palette?" switch. For Mindstream this suggests each tool's registry entry carry: accepted shape (text / prompt list), mode (ASK / SEND), a label, and an optional availability predicate evaluated by the shell (for example "runner is idle").
- JupyterLab's "restore = re-execute a command with saved JSON args" means a tool's public command and its restore path are the same code. Mindstream could make "open tool X at place Y" a registry command, used both by Send-to and by session restore.
- Obsidian shows the cost of a thin official surface: URI running of commands, callbacks, and workspace loading all had to be supplied by community plugins, and breaking changes land on users. As Mindstream's tools are all first-party, the lesson is to keep the registry contract tiny and versioned rather than expose internals.
- Raycast's rule "position in the list defines the default" is a cheap way to give every text item one obvious action (Return) while keeping the rest one keystroke away.

### Gaps
- Not verified this session (hosts blocked or no result): VS Code contribution-point `group` ordering syntax (believed `navigation` group first and `group@order`), webview messaging; JupyterLab launcher, MIME renderer `rank`, command `isEnabled/isVisible`; Obsidian core `registerView` / `addCommand` and the core Workspaces plugin's behaviour.
- No sourced material was gathered for Emacs/Org-mode, Notion, Anytype, Tana, TiddlyWiki, Coda Packs. Unverified background: Emacs composes through shared buffers and interactive commands (everything is text in a buffer, any command can act on any buffer), which is the purest "shared model" extreme; Coda Packs declare typed formulas and actions; Tana uses command nodes over supertagged nodes; TiddlyWiki treats every tool as tiddlers in one store. These should be checked before being stated in the report.

## 2. Uniform "send / share / open with" actions

### Takeaway
The systems that work give one consistent entry point, filter targets by declared content type before showing anything, cap the number of slots, and let usage (not the developer) set the order. The recurring failure is an unbounded, self-registering list: iOS's share sheet and the macOS Services menu both drew clutter complaints until users were given edit, pin and hide controls.

### Cited Findings
- Android draws a sharp line between two UIs: the Sharesheet is "primarily designed for sending content outside your app", while the intent resolver "is best suited for passing data to the next stage of a well-defined task"; if only one app matches the resolver, it simply runs — [Android: send simple data](https://developer.android.com/training/sharing/send)
- Android instructs developers: "Don't display your app's own list of share targets or create your own Sharesheet variations"; the system sheet "uses a consistent ranking" because it "can take into account information about app and user activity that is only available to the system" — [Android: send simple data](https://developer.android.com/training/sharing/send)
- Type filtering: senders should provide "the most specific MIME type available"; `*/*` is discouraged "because most receiving apps aren't able to receive any kind of content" — [Android: send simple data](https://developer.android.com/training/sharing/send)
- Preview before send: since Android 10 the sheet previews the text being shared, with an optional title and thumbnail, because "a richer preview can reassure your users what is being shared" — [Android: send simple data](https://developer.android.com/training/sharing/send)
- Hard caps: at most two caller-supplied custom targets via `EXTRA_INITIAL_INTENTS`, and "every custom Intent that you add reduces the number the system suggests. In general, avoid adding custom targets"; Android 14 added custom actions shown as small icons at the top of the sheet — [Android: send simple data](https://developer.android.com/training/sharing/send)
- Self-exclusion: `EXTRA_EXCLUDE_COMPONENTS` is commonly used "to hide your app's share targets when your users share from within your app" — [Android: send simple data](https://developer.android.com/training/sharing/send)
- The sender can learn which target was chosen via an `IntentSender` callback carrying `EXTRA_CHOOSER_RESULT` — [Android: send simple data](https://developer.android.com/training/sharing/send)
- Direct Share ranking: the sheet "shows a fixed number of Direct Share targets ... sorted by rank"; apps publish shortcuts in importance order ("a lower index indicates more importance"), report usage on each real use, keep ids stable so usage history is retained, and must not publish stale targets ("a conversation with no user activity in the last 30 days is considered stale") — [Android: Direct Share targets](https://developer.android.com/training/sharing/direct-share-targets)
- Direct Share landing rule: tapping a target must take the user straight to the place where the action happens; "Don't present the user a disambiguation UI" — [Android: Direct Share targets](https://developer.android.com/training/sharing/direct-share-targets)
- Direct Share history lesson: the original API retrieved targets "reactively on demand, leading to a slow loading time"; Android 10 replaced it with targets published in advance, and Android 11 deprecated the old service — [Android: Direct Share targets](https://developer.android.com/training/sharing/direct-share-targets)
- iOS: Apple's guidance says people can edit the action list so it shows the ones they use most; share extensions should prefer the system composition view for consistency — [Apple HIG: activity views](https://developer.apple.com/design/human-interface-guidelines/activity-views.md)
- iOS complaints: because apps register themselves, "your list of options can quickly get cluttered" — [Six Colors](https://sixcolors.com/?p=19105); users complained the action list became "long and cumbersome" — [Computerworld](https://www.computerworld.com/article/1671419/how-to-use-the-new-share-button-in-ios-13-ipados.html); the Edit Actions screen is hard to understand and use with VoiceOver — [AppleVis bug report](https://applevis.com/bugs/ios/edit-actions-screen-share-sheet-difficult-understand-use)
- iOS 26 reportedly shows fewer actions up front, keeping Edit Actions at the bottom to pin favourites, hide unused items and reorder (single secondary report) — [AppleInsider forum post](https://forums.appleinsider.com/discussion/240642)
- macOS Services: apps advertise services in `NSServices` in Info.plist with `NSSendTypes` / `NSReturnTypes`; the menu is filtered by the pasteboard types the current selection can send and receive — [Apple: Services properties](https://developer.apple.com/library/mac/documentation/Cocoa/Conceptual/SysServices/Articles/properties.html)
- macOS Services can be request-and-return: the selected text is passed to the provider and the processed result replaces the original selection — [Nil Coalescing: macOS system-wide services](https://nilcoalescing.com/blog/macOSSystemWideServices)
- macOS Services criticism: "since many applications install their entries without asking the user, the macOS services menu tends to clog up with dozens of entries quickly" — [Wikipedia: Services menu](https://en.wikipedia.org/wiki/Services_menu)
- Plan 9 plumber: a rules file of pattern/action rules routes formatted text messages; the first matching rule wins; apps send by writing to `/mnt/plumb/send` and receive by reading named "ports" such as `edit` or `web`, and one port can be read by several applications — [plumb(6) man page](https://src.rcs.uwaterloo.ca/xref/plan9/sys/man/6/plumb), [Pike, "Plumbing and Other Utilities"](https://static.usenix.org/event/usenix2000/general/full_papers/pikeplumb/pikeplumb_html/index.html)
- Plumber design rationale: the message content, interpreted by the rules, decides the destination, so the user does not pick a target or move data by hand — [Pike, USENIX 2000](https://static.usenix.org/event/usenix2000/general/full_papers/pikeplumb/pikeplumb_html/index.html)
- Plumber wart: ports are created per unique destination in the rules and never deleted automatically, even after rules change — [plumber(4) man page](https://src.rcs.uwaterloo.ca/source/xref/plan9/sys/man/4/plumber)
- Web Share Target (receiving shares into a web app): works in Chrome 76+ on Android and Chrome 89+ on desktop, only once the web app is installed — [Chrome for Developers: Web Share Target](https://developer.chrome.com/articles/web-share-target); Safari is listed as not supported through 26.5 — [caniuse: share targets](https://caniuse.com/wf-app-share-targets)
- Web Share (sending, `navigator.share`) is a W3C Recommendation but MDN marks it "Limited availability" — [W3C Web Share](https://www.w3.org/TR/web-share/), [MDN Web Share API](https://developer.mozilla.org/docs/Web/API/Web_Share_API)

### Inferences
- Android's Sharesheet-versus-resolver split maps directly onto Mindstream's SEND versus ASK: a broad "send it somewhere" picker versus "pass this to the next stage of a defined task". The resolver's rule "if exactly one target matches, skip the chooser" is worth copying for ASK, since with two tools the picker would usually be a pointless click.
- A concrete rule set for "Send to…" follows from the evidence: (1) build the list only from registry entries accepting the item's shape; (2) exclude the originating tool by default; (3) show a short preview of the text being sent; (4) order by recent use with stable ids, allow pinning; (5) cap visible slots and push the rest behind "more"; (6) land the user directly at the place where the content arrived, no second question.
- The plumber is the opposite philosophy (zero chooser, rules decide). For a single-user app it suggests a later enhancement: a default target per content shape, with the picker only on a modifier key.
- Web Share Target is a poor foundation for Mindstream's external intake: Chromium-only and requires installation. In-app registry hand-off does not depend on it.

### Gaps
- Could not read Pike's paper directly, so the acme button-3 gesture, behaviour when no rule matches, and Pike's own list of limitations are unverified. Unverified background: plumbing is one-way with no reply channel, and a non-running target can be launched by a `plumb start` rule.
- No sourced detail gathered on Drafts action list/action bar UI, PopClip, iOS action-extension versus share-extension distinction, Quick Actions in Finder, or Obsidian "send to" plugins.
- How iOS ranks the suggestions row was not found in any source.

## 3. Request-and-return hand-offs

### Takeaway
Every mature system treats "ask and get an answer" as two separately failing stages (delivery, then result) with a named error for each, a bounded wait, and an explicit cancel path distinct from error. The origin-is-gone problem is solved by making the pending request durable data rather than a live callback.

### Cited Findings
- FDC3: `raiseIntent` returns a promise for an `IntentResolution`; the caller may optionally await `getResult()`, which yields a single `Context`, a `Channel` (for a stream of responses), or void — [FDC3 2.2 API spec](https://raw.githubusercontent.com/finos/FDC3/main/website/versioned_docs/version-2.2/api/spec.md)
- FDC3 requires agents to "provide a method of resolving ambiguous intents"; "a common method is to display a UI that allows the user to pick the desired App from a list", and "Desktop Agents may resolve intents by any suitable methodology" — [FDC3 2.2 API spec](https://raw.githubusercontent.com/finos/FDC3/main/website/versioned_docs/version-2.2/api/spec.md)
- FDC3 timeouts: agents must allow "by default, at least a 15 second timeout" for a launched app to add its listeners; handlers "SHOULD be registered via `fdc3.addIntentListener` within 15 seconds of the application launch"; implementations "MAY support longer timeouts". No timeout is specified for how long a handler may take to produce a result — [FDC3 2.2 API spec](https://raw.githubusercontent.com/finos/FDC3/main/website/versioned_docs/version-2.2/api/spec.md)
- FDC3 resolution-stage errors (`ResolveError`): `NoAppsFound`; `UserCancelled` ("if the user cancelled the resolution request, for example by closing or cancelling a resolver UI"); `ResolverTimeout` ("if a timeout cancels an intent resolution that required user interaction"); `TargetAppUnavailable`; `TargetInstanceUnavailable` ("for example because it has been closed"); `IntentDeliveryFailed` (target did not add a handler in time); `MalformedContext`; `ApiTimeout` — [FDC3 2.2 Errors reference](https://raw.githubusercontent.com/finos/FDC3/main/website/versioned_docs/version-2.2/api/ref/Errors.md)
- FDC3 result-stage errors (`ResultError`): `NoResultReturned` ("the intent handler exited without returning a valid result"), `IntentHandlerRejected` (handler threw or rejected), `ApiTimeout` ("a timeout occurs before the getResult() API call is resolved") — [FDC3 2.2 Errors reference](https://raw.githubusercontent.com/finos/FDC3/main/website/versioned_docs/version-2.2/api/ref/Errors.md)
- FDC3 origin identity: agents should give the receiving app metadata about each message including the originating app, but receivers must cope with its absence because it is optional — [FDC3 2.2 API spec](https://raw.githubusercontent.com/finos/FDC3/main/website/versioned_docs/version-2.2/api/spec.md)
- Android: while another activity is producing a result it is "possible—and, in cases of memory-intensive operations ... almost certain—that your process and your activity will be destroyed". Therefore the Activity Result APIs "decouple the result callback from the place in your code where you launch the other activity", and the callback "must be unconditionally registered every time your activity is created" — [Android: get a result from an activity](https://developer.android.com/training/basics/intents/result)
- Android: "any additional state needed to handle the result must be saved and restored separately"; callbacks must be registered in the same order on each creation "so that the inflight results are delivered to the correct callback" — [Android: get a result from an activity](https://developer.android.com/training/basics/intents/result)
- Android: a typed `ActivityResultContract` declares input and output types; cancellation arrives as `RESULT_CANCELED` and the sample contract maps anything other than `RESULT_OK` to null; the registry can be swapped for a fake that calls `dispatchResult()` so request/return can be tested without launching the other app — [Android: get a result from an activity](https://developer.android.com/training/basics/intents/result)
- x-callback-url: the source passes `x-success`, `x-error` and (added in a later revision) `x-cancel` URLs plus `x-source`, the friendly name of the calling app, which the target may show to the user; if `x-success` is omitted the user is assumed to stay in the target app — [Apple Shortcuts guide: x-callback-url](https://support.apple.com/guide/shortcuts/apdcd7f20a6f/), [MacStories on x-cancel](https://www.macstories.net/linked/designing-an-x-callback-url-action-with-x-cancel-parameter/)
- Drafts: with "wait for response" on, `x-success` continues the action with results in `context.callbackResponses`, `x-cancel` cancels the action, `x-error` fails it and logs; Drafts waits 120 seconds then cancels the remainder of the action; the script API exposes status values including `timeout` — [Drafts docs: advanced steps](https://docs.getdrafts.com/docs/actions/steps/advanced), [Drafts script reference: CallbackURL](https://beta-scripting.getdrafts.com/classes/CallbackURL)
- Drafts user-reported failure: a callback "hangs if app does not return" — [Drafts forum](https://forums.getdrafts.com/t/callbackurl-hangs-if-app-does-not-return/2633); and the action panel not closing after a successful callback, worked around with `app.hideActionList()` — [Drafts forum](https://forums.getdrafts.com/t/drafts-not-closing-the-actions-panel-after-successful-x-callback-url/10280)
- LSP: client and server exchange capability sets during the `initialize` request/response; current spec is 3.18 with 3.17 previous — [LSP 3.17 specification](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/), [LSP 3.18 specification](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.18/specification)

### Inferences
- A minimal ASK state machine consistent with all four systems: `pending-delivery → delivered → answered | cancelled | failed | timed-out`, with user cancel kept distinct from failure (FDC3 `UserCancelled`, x-callback `x-cancel`, Android `RESULT_CANCELED`). Mindstream's broker should stay dumb but must stamp each ASK with an id and origin so these states are observable.
- Android's lesson is the one most relevant to "reopening restores each tool's place": persist the pending ASK (id, origin tool, origin location, sent text) in the shell's store, and have the origin tool re-register its result handler on mount. Then a reload mid-ASK is the same case as "origin was closed", not a special one.
- When the origin is gone at answer time, FDC3 offers no rule. The natural fallback for Mindstream is to route the orphaned answer to the shelf, labelled with its origin, rather than drop it.
- No standard sets a deadline for a human-paced answer (FDC3 times out only on launch and listener registration; Drafts' 120 s is for machine callbacks and users report hangs). Since a Mindstream ASK may wait on the user working in another tool, a visible "waiting on Runner" chip with a cancel control is more appropriate than a timer.
- `x-source` is the only widely deployed mechanism found for telling the user who asked. Showing "Asked by Pad · returns to paragraph N" as a banner in the callee is the direct analogue.

### Gaps
- No source describes the resolver UI layout or "remember my choice" behaviour in OpenFin/Here, io.Connect, Finsemble or Connectifi; vendor docs were not reachable. `ContextMetadata.source` by name, and AppD `resultType`, were not confirmed in the page read.
- The x-callback-url spec site was blocked; behaviour when no callback ever fires is unspecified in anything read (consistent with it being a convention, but unverified).
- LSP `$/cancelRequest`, the `RequestCancelled` error code and dynamic capability registration were not confirmed from the spec text. VS Code `executeCommand` return values were not sourced.

## 4. Shelves, trays and inboxes for content in transit

### Takeaway
Sourced evidence here is thin. What was found supports two rules: a shelf should be summoned by the act of moving something rather than be a permanent place, and anything stale should be pruned by rule. Android's 30-day staleness rule for share targets is the clearest codified expiry heuristic found.

### Cited Findings
- Dropover (macOS): floating shelves opened by a shake gesture while dragging (its signature method), or by keyboard shortcut or menu bar; supports multiple shelves; requires macOS 13+; a recent update added auto-closing the detail view on outside click — [Dropover on the Mac App Store](https://apps.apple.com/app/dropover-easier-drag-drop/id1355679052?mt=12)
- Yoink (macOS): "a temporary 'shelf' for your files and app-content"; listed at $8.99 — [Yoink on the Mac App Store](https://apps.apple.com/app/id457622435); a forum user notes Dropover allows multiple shelves where Yoink does not — [Mac Power Users forum](https://talk.macpowerusers.com/t/dropover-mac-shelf/18201)
- Staleness rule from an adjacent domain: Android tells apps not to publish share targets with no activity in the last 30 days — [Android: Direct Share targets](https://developer.android.com/training/sharing/direct-share-targets)
- Generic triage guidance: capture, process and organise should be separate motions; an inbox is a triage zone where each item eventually needs a decision — [ByDesign help: Inbox](https://bydesign.featurebase.app/help/articles/6997140-inbox) (low-authority source, a product help page)
- Arc (whose Library and Easel were suggested comparables) went into maintenance mode in May 2025 — [The Register](https://www.theregister.com/2025/05/27/arc_browser_development_ends/); Atlassian agreed to acquire The Browser Company for about $610 million — [Neowin](https://www.neowin.net/news/atlassian-acquires-the-browser-company-creators-of-arc-browser/); a TechCrunch headline dated 22 October 2026 reports Arc sunsets on 22 December 2026 with migration to Dia — [TechCrunch](https://techcrunch.com/2026/10/22/arc-browser-sunsets-december-22-as-the-browser-company-doubles-down-on-dia/)
- Muse (canvas app with an inbox) is still shipping: changelog shows 3.4.5 (July 2025, dark mode) and 3.5.2 (22 February 2026), and an entry announcing "Muse is now Allume!" — [Allume updates](https://allume.com/updates/); the App Store listing still reads "Muse — canvas for ideas" — [App Store](https://apps.apple.com/us/app/muse-canvas-for-ideas/id1501563902)

### Inferences
- Dropover and Yoink are "transit" shelves: they appear when a drag starts and are expected to empty. Inboxes (Readwise Reader, Tana, Notion) are "intake" queues that require triage. Mindstream's shelf, described as a tray any tool can drop to or pull from, is the transit kind, so it should favour: appearing on demand, showing a count badge, showing each item's origin tool and age, and one-click "pull into current tool".
- To avoid a dumping ground, candidate mechanics are: age shown on every item; auto-archive after N days (30 has precedent); a soft cap with the oldest items greying out; "pull" defaults to move rather than copy so the shelf drains through use.
- Arc should be cited only as a design reference, not as a live product, given the reported sunset.

### Gaps
- No sourced findings on: Gladys, iPadOS Shelf/Stage Manager, Muse inbox design, Arc Library/Easel behaviour, clipboard managers (Paste, Maccy, Raycast clipboard history) and their retention defaults, Heptabase/Scrintal card library, Notion inbox, Readwise Reader inbox/later/archive, Tana inbox, Drafts inbox. The one targeted search returned only generic email-triage material.
- Unverified background worth checking: Drafts treats the inbox as the default home of every new draft, with archive and flag as the triage outcomes; Readwise Reader splits into Inbox / Later / Archive; clipboard managers typically cap history by count or age.
- No evidence was found for or against required-triage designs.

## 5. Multi-tool layouts that restore state

### Takeaway
The robust restoration design is to save a description of how to recreate each pane (command plus arguments) rather than the pane itself, and to store named layouts separately from tool data. On caller/callee placement, cognitive research favours side-by-side when the user must integrate the two sources, and is neutral or negative otherwise.

### Cited Findings
- JupyterLab: after the shell finishes restoring the layout, the application's `restored` promise resolves; plugins are restored by executing their registered command with saved args; the docs describe the lifecycle as "subtle" — [JupyterLab LayoutRestorer API](https://jupyterlab.readthedocs.io/en/4.4.x/api/classes/application.LayoutRestorer-1.html)
- JupyterLab workspaces "contain the state of JupyterLab: the files that are currently open, the layout of the application areas and tabs, etc. When the page is refreshed, the workspace is restored"; workspaces are named in the URL (`/lab/workspaces/foo`), copied with `?clone` and cleared with `?reset` — [JupyterLab URLs docs](https://jupyterlab.readthedocs.io/en/latest/user/urls.html)
- JupyterLab failure mode: users recover from a stuck workspace by closing all tabs and opening the `?reset` URL; workspace files live in `~/.jupyter/lab/workspaces/` — [NCAR Zulip archive](https://ncar.github.io/zulip-archive/stream/16-jupyterlab-hub/topic/resume.20jupyterhub.20with.20previously.20opened.20tabs.html)
- JupyterLab regression report: clone-and-link workflows broke in 3.0.x after working in 2.3.1 — [Jupyter Discourse](https://discourse.jupyter.org/t/i-can-not-open-more-than-one-notebook-in-the-same-workspace-with-links-any-longer-in-jl-3/9211)
- Obsidian stores saved workspaces in `.obsidian/workspaces.json` inside the vault, and loading a workspace by URI was the original purpose of the Advanced URI plugin — [Obsidian Hub guide](https://publish.obsidian.md/hub/04+-+Guides%2C+Workflows%2C+%26+Courses/Guides/Controlling+Obsidian+via+a+Third-party+App), [Advanced URI docs](https://publish.obsidian.md/advanced-uri-doc/Home)
- Split attention: when sources must be mentally combined, dividing attention across locations costs resources for search-and-match — [Wikipedia: Split-attention effect](https://en.wikipedia.org/wiki/Split-attention_effect)
- Jang, Schunn and colleagues compare spatially distributed (side-by-side) with stacked (overlapping) displays for integrative tasks, citing the proximity compatibility principle: high perceptual proximity when information must be integrated — [Jang, Schunn & Nokes 2011](https://www.lrdc.pitt.edu/Schunn/papers/jang-schunn-nokes2011.pdf), [Jang & Schunn 2012](https://www.lrdc.pitt.edu/Schunn/papers/JangSchunn2012-ACP.pdf)
- Android's Direct Share rule that the callee must open directly on the relevant item, with the shared content prefilled, is also a layout rule for hand-offs — [Android: Direct Share targets](https://developer.android.com/training/sharing/direct-share-targets)

### Inferences
- Borrow JupyterLab's model: the shell persists a layout tree plus, per pane, `{toolId, restoreArgs}`; each tool supplies a pure "restore from args" entry. Provide an escape hatch equivalent to `?reset`, because a corrupt saved layout that blocks startup is a documented real-world failure.
- Guidance on caller/callee placement derived from the research: for ASK, where the user will compare the request with the answer and the answer lands back at the origin, open the callee beside the caller. For SEND, where the origin's job is done, either replace or leave the layout unchanged and just badge the target; forcing a split adds a second focus for no integrative benefit.
- Named, URL-addressable workspaces are cheap in a browser app (a hash or query parameter selects the layout record) and give "clone" and "reset" for free.

### Gaps
- No usability study directly comparing split view with replace/modal for hand-offs was found; Nielsen Norman Group material did not surface. The split-attention literature is from instructional design and is applied here by analogy.
- Not sourced: VS Code editor groups and Zen mode, Obsidian Sliding Panes (unverified background: its ideas were absorbed into core stacked tabs around Obsidian 1.0), Arc/Vivaldi tiling, Notion side peek, Muse boards, Heptabase tabs.

## 6. Shared content models versus message passing

### Takeaway
The strongest contemporary argument (Ink and Switch) is for tools operating over shared, user-owned data rather than siloed apps, but its authors concede that interoperability and schema agreement remain unsolved. Message passing with a tiny vocabulary sidesteps that open problem at the price of copies instead of live references, which is a reasonable trade for one developer.

### Cited Findings
- Ink and Switch, "Malleable Software: Restoring User Agency in a World of Locked-Down Apps" (June 2025) defines malleable software as an ecosystem where anyone can adapt their tools with minimal friction, and argues for a gentle slope from user to creator, "tools, not apps", and communal creation, illustrated by a knife versus an avocado slicer — [Ink and Switch essay](https://www.inkandswitch.com/essay/malleable-software/), [Simon Willison's summary](https://simonwillison.net/2025/Jun/11/malleable-software)
- The essay presents the lab's prototypes Patchwork, Potluck ("dynamic documents as personal software") and Embark ("dynamic documents for making plans"), and builds on local-first principles of user ownership of data — [Ink and Switch essay](https://www.inkandswitch.com/essay/malleable-software/)
- The essay acknowledges open questions: how smaller pieces of code can be shared and collaboratively developed, and "how interoperability can be maintained" — [Ink and Switch essay](https://www.inkandswitch.com/essay/malleable-software/) (as reported in search summary)
- Fowler and Lewis: "The microservice community favours an alternative approach: smart endpoints and dumb pipes"; the pipe is dumb in that it "acts as a message router only" — quoted in [Nordic APIs](https://nordicapis.com/what-does-smart-endpoints-and-dumb-pipes-mean/)
- Their target is the ESB, which accumulates routing, choreography, transformation and business rules; applications should "aim to be as decoupled and as cohesive as possible" (secondary quotation, not checked against the original) — [Intellyx](https://intellyx.com/2015/03/11/microservices-avoiding-dumb-pipes/)
- Counterpoint: Intellyx argues "dumb" muddies the discussion and that pipes still need to be capable infrastructure — [Intellyx](https://intellyx.com/2015/03/11/microservices-avoiding-dumb-pipes/)
- The plumber is a deliberate middle position: endpoints stay ignorant of each other, but the pipe holds user-editable routing rules, so the intelligence in the middle belongs to the user, not to an integration team — [Pike, USENIX 2000](https://static.usenix.org/event/usenix2000/general/full_papers/pikeplumb/pikeplumb_html/index.html)
- FDC3 keeps the shared vocabulary small and typed: intents take a context type and results are limited to a context, a channel, or nothing — [FDC3 2.2 API spec](https://raw.githubusercontent.com/finos/FDC3/main/website/versioned_docs/version-2.2/api/spec.md)
- Cost of a shared model under migration: Logseq's move from Markdown files to a database graph required refactoring plugin libraries and, as of May 2026, only a first round-trip between DB graphs and on-disk Markdown had shipped, with two-way sync still on a feature branch — [Logseq DB update, 16 May 2026](https://discuss.logseq.com/t/whats-new-with-logseq-db-may-16th-2026/35020)

### Inferences
- The two camps optimise for different things. Shared-document products (Notion, Anytype, Tana, Capacities, Logseq) get live references and universal views but make every tool depend on one schema, so a schema change is a migration for everything (Logseq is the visible example). Message-passing suites get independent tools and trivial contracts but produce copies that drift.
- Mindstream's two shapes (text, ordered prompt list) are the equivalent of FDC3 context types pared to a minimum. The risk to watch, by analogy with the ESB critique, is logic creeping into the broker (transformations, conditional routing). The routing-slip idea keeps that logic in the message, not the pipe, which is consistent with the Fowler position.
- The drift problem of copies can be softened without a shared model by carrying provenance in the message envelope (origin tool, origin location, timestamp), which also serves the "who asked" banner and shelf labelling.
- The Ink and Switch position is a caution that Mindstream's tools should not harden into mini-apps: the uniform Send-to and shelf are what make them feel like tools on common material.

### Gaps
- Neither the Ink and Switch essay nor Fowler's article could be read directly; quotations are via secondary pages and should be checked before being presented as verbatim.
- No sourced critique of over-general plugin APIs, of "Unix philosophy for apps", or of block-model products by their builders was obtained. Hohpe and Woolf's routing-slip page was not fetched.

## 7. Solo-developer lessons

### Takeaway
No first-person retrospective from a solo developer who built a plugin host was found; this is a real gap. The indirect evidence from platform histories points one way: start with the smallest declarative contract, have targets declared in advance rather than discovered on demand, and expect that anything exposed becomes a compatibility burden.

### Cited Findings
- A targeted search for solo-developer retrospectives on plugin systems returned nothing on topic; one plugin developer in an OpenAI community thread asked for documented good practice on designing services and APIs for plugins, suggesting such guidance is scarce — [OpenAI community thread](https://community.openai.com/t/what-are-the-top-3-pain-points-for-plugin-developers/222840?page=2)
- Platform reversal 1: Android's first Direct Share design queried apps on demand and was slow; it was replaced by targets published in advance and the original API was deprecated within about five years — [Android: Direct Share targets](https://developer.android.com/training/sharing/direct-share-targets)
- Platform reversal 2: VS Code removed the need for authors to hand-declare `onCommand` activation events in 1.74, deriving them from the command contribution — [VS Code command guide](https://code.visualstudio.com/api/extension-guides/command)
- Platform reversal 3: Android replaced `startActivityForResult` / `onActivityResult` with typed contracts and an injectable registry, citing process death and testability — [Android: get a result from an activity](https://developer.android.com/training/basics/intents/result)
- Exposed surface becomes debt: Obsidian's API changelog records removed functions and long-standing developer confusion, and users bear the breakage on update — [Obsidian API changelog](https://unpkg.com/obsidian@1.13.1/CHANGELOG.md), [Obsidian forum](https://forum.obsidian.md/t/problems-updating-to-version-1-7-4-with-64-plugins/90675/9)
- Features left to the community when the core is small: Obsidian's command-by-URI, workspace-by-URI and x-callback returns all come from community plugins — [Advanced URI docs](https://publish.obsidian.md/advanced-uri-doc/Home), [Actions URI callbacks](https://czottmann.github.io/obsidian-actions-uri/callbacks/)
- A small team can keep a tool-like product alive long term: Muse continues to ship under the Allume name with releases through February 2026 — [Allume updates](https://allume.com/updates/)

### Inferences
- Suggested build order, derived from what platforms kept versus reversed: (1) static registry entries per tool and a Send-to menu built from them; (2) SEND; (3) ASK with a persisted pending record and explicit cancel; (4) layout restore via the same "open with args" command; (5) shelf; (6) ranking and pinning; and only much later, if ever, user-editable routing rules or third-party tools.
- Likely over-engineering for a two-tool, single-user app: a resolver UI when only one target matches, dynamic runtime registration, typed result channels/streams (FDC3's `Channel` result), timeouts tuned for unreliable remote apps, and any plugin sandboxing.
- Android's injectable `ActivityResultRegistry` suggests making the broker replaceable by a fake in tests from day one; it is cheap and is the main way to test hand-offs without mounting two tools.

### Gaps
- No write-ups from solo or small-team builders of plugin hosts (for example TiddlyWiki, Logseq plugin authors, Raycast extension authors, Obsidian plugin authors on API design) were retrieved. Hacker News discussions were not searched successfully. This question remains largely unanswered by evidence.
