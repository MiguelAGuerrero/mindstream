## 1. FDC3 (fdc3.finos.org, current version)

### Takeaway
The current FDC3 Standard is now 3.0 (adopted 26 October 2026), not 2.2 as the earlier notes assumed; the intent, result and error mechanics the earlier notes described survive unchanged, and 3.0 adds delivery metadata that maps closely onto Mindstream's envelope: a `source`, a `timestamp` and an always-present `traceId` that the broker must forward unchanged. The spec leaves the resolver UI deliberately unstandardised and tells the Desktop Agent it must not inspect, strip or modify app-provided signature fields, and must forward app-provided metadata unchanged.

### Cited Findings

Version and status
- **CORRECTED.** Current stable version is 3.0; past versions listed are 2.2, 2.1, 2.0, 1.2, 1.1, 1.0. The earlier notes treated 2.2 as current and listed "whether FDC3 has moved beyond 2.2" as a gap — [FDC3 Versions](https://fdc3.finos.org/versions)
- **NEW.** The abstract page reads "FDC3 3.0 / Status: Current / adopted: 26th October 2026"; spec pages are stamped "Last updated on Oct 8, 2026" — [FDC3 Standard abstract](https://fdc3.finos.org/docs/fdc3-standard)
- **NEW.** "The Standard currently consists of five complementary parts: API, Intents, Context Data, App Directory, Agent Bridging" — [FDC3 Introduction](https://fdc3.finos.org/docs/fdc3-intro)

Desktop Agent (the broker) and what is standardised
- **NEW.** "A Desktop Agent is a desktop component (or aggregate of components) that serves as a launcher and message router (broker) for applications in its domain." — [API Overview 3.0](https://fdc3.finos.org/docs/api/spec)
- **NEW.** "In FDC3, applications communicate through a Desktop Agent rather than directly with each other... applications themselves have no direct relationship with their counterparts." — [API Overview 3.0](https://fdc3.finos.org/docs/api/spec)
- **NEW.** The spec says its own surface is small relative to an implementation, and lists as *not* standardised: "Workspace management", "User identity and SSO", "Entitlements", "UX of application resolution" — [API Overview 3.0](https://fdc3.finos.org/docs/api/spec)
- **NEW.** Design stance: "standards should be optimized for ease of adoption rather than functional completeness. Functionality absent from a FDC3 specification is in no way a commentary on its importance." — [API Overview 3.0](https://fdc3.finos.org/docs/api/spec)

Intents
- **NEW (exact definition).** "FDC3 Intents define a standard set of verbs that, in conjunction with context data acting as nouns, can be used to put together common cross-application workflows on the financial desktop." Also: "Intents are not full RPC, apps don't need to enumerate every function with an intent." — [Intents Overview 3.0](https://fdc3.finos.org/docs/intents/spec)
- **NEW.** "Raising an Intent is a method for an application to request functionality from another application and, if desired, defer the discovery and launching of the destination app to the Desktop Agent." — [API Overview 3.0](https://fdc3.finos.org/docs/api/spec)
- **NEW.** Three interop models for intents: "Chain: In this case the workflow is completely handed off from one app to another (similar to linking). Currently, this is the primary focus in FDC3." / "Client-Service: A Client invokes a Service via the Intent, the Service performs some function, then passes the workflow back to the Client." / "Remote API" — [API Overview 3.0](https://fdc3.finos.org/docs/api/spec)
- **NEW.** Desired characteristics of an intent include "Stateless — Workflows should not require callbacks or endpoints to maintain references to each other. Once an Intent is passed to an endpoint - it controls the rest of that workflow." and "Specific", "Distinct", "Recognizable", "Repeatable" — [Intents Overview 3.0](https://fdc3.finos.org/docs/intents/spec)
- **NEW.** Name prefixes carry expected behaviour: `View___` ("Content should be displayed to the user"), `Start___` ("An interaction, such as a chat room or email thread, should be initiated"), and since 2.0 `Create___`, `Update___`, `CreateOrUpdate___`, `Delete___`, `Get___` ("A record or entity should be retrieved and returned as an intent result"), `Share___` — [Intents Overview 3.0](https://fdc3.finos.org/docs/intents/spec)
- **NEW.** Standard intents list (3.0): CreateInteraction, CreateOrUpdateProfile, GetUser, StartCall, StartChat, StartEmail, ViewAnalysis, ViewChat, ViewChart, ViewHoldings, ViewInstrument, ViewInteractions, ViewMessages, ViewNews, ViewOrders, ViewProfile, ViewQuote, ViewResearch. Deprecated: ViewContact — [Intents Overview 3.0](https://fdc3.finos.org/docs/intents/spec)
- **NEW.** Proprietary intents: "All standard intent names are reserved... The recommended approach is to namespace the intent with the application name." — [Intents Overview 3.0](https://fdc3.finos.org/docs/intents/spec)

Context
- **NEW (exact definition).** "FDC3 Context Data defines a standard for passing common identifiers and data, encoded in JSON, between apps to create a seamless workflow... The focus is on providing a standard JSON payload structure that can be used to establish a lowest common denominator for interoperability." — [Context Data 3.0](https://fdc3.finos.org/docs/context/spec)
- **NEW.** The whole base contract is `interface Context { type: string; name?: string; id?: { [x:string]: string }; [x: string]: any; }`. "The `type` property is the only required part of the FDC3 context data schema. The FDC3 API relies on the `type` property being present to route shared context data appropriately." Assumption 1: "Context data objects are identified and routed according to their type, which is unique." — [Context Data 3.0](https://fdc3.finos.org/docs/context/spec)
- **NEW.** Two use cases: "Transmitting reference data between applications" (send identifiers, the target looks the entity up) and "Transferring information between applications" ("it is instead the data itself being transferred") — [Context Data 3.0](https://fdc3.finos.org/docs/context/spec)
- **NEW.** Standard context types (3.0): fdc3.action, fdc3.chart, fdc3.chat.initSettings, fdc3.chat.message, fdc3.chat.room, fdc3.chat.searchCriteria, fdc3.contact, fdc3.contactList, fdc3.country, fdc3.currency, fdc3.email, fdc3.instrument, fdc3.instrumentList, fdc3.interaction, fdc3.message, fdc3.organization, fdc3.portfolio, fdc3.position, fdc3.nothing, fdc3.timeRange, fdc3.transactionResult, fdc3.valuation. Experimental: fdc3.order, fdc3.orderList, fdc3.product, fdc3.trade, fdc3.tradeList — [Context Data 3.0](https://fdc3.finos.org/docs/context/spec)
- **NEW.** `fdc3.nothing` is an explicit "no context" type: "By using an explicit type to represent an absence of context we allow applications to declare their support for an absence of context." — [Intents Overview 3.0](https://fdc3.finos.org/docs/intents/spec)

raiseIntent, raiseIntentForContext, getResult
- **CONFIRMED, signature CORRECTED for 3.0.** `raiseIntent(intent: string, context?: Context | null, app?: AppIdentifier | null, newInstance?: boolean | null, metadata?: AppProvidableContextMetadata): Promise<IntentResolution>`. "Raises a specific intent for resolution against apps registered with the desktop agent." The `newInstance` and `metadata` parameters are additions relative to what the earlier notes described — [DesktopAgent reference 3.0](https://fdc3.finos.org/docs/api/ref/DesktopAgent)
- **CONFIRMED.** `raiseIntentForContext(context, app?, newInstance?, metadata?)`: "Finds and raises an intent against apps registered with the desktop agent based purely on the type of the context data." It is like `findIntentsByContext` then raise, "except in this case the desktop agent has the opportunity to provide the user with a richer selection interface where they can choose both the intent and target app." — [DesktopAgent reference 3.0](https://fdc3.finos.org/docs/api/ref/DesktopAgent)
- **CONFIRMED.** "Issuing apps may optionally wait on the promise that is returned by the `getResult()` member of the `IntentResolution`. This promise will resolve when the receiving app's intent handler function returns and resolves a promise. The Desktop Agent resolves the issuing app's promise with the Context object, Channel object or void that is provided as resolution within the receiving app." — [DesktopAgent reference 3.0](https://fdc3.finos.org/docs/api/ref/DesktopAgent)
- **CONFIRMED.** `IntentResolution` has `source: AppIdentifier` ("`source.instanceId` MUST be set"), `intent: string`, `getResult(): Promise<IntentResolutionResult>`, and (3.0) `getResultMetadata(): Promise<ContextMetadata>`. `type IntentResult = Context | ContextWithMetadata | Channel | void` — [Types reference 3.0](https://fdc3.finos.org/docs/api/ref/Types)
- **CONFIRMED.** Two-stage failure: `raiseIntent` rejects with a `ResolveError`; `getResult()` rejects with a `ResultError` "if: (1) the intent handling function's returned promise rejects, (2) the intent handling function doesn't return a valid response (a promise or void), or (3) the returned promise resolves to an invalid type." — [DesktopAgent reference 3.0](https://fdc3.finos.org/docs/api/ref/DesktopAgent)
- **NEW.** Delivery is acknowledged before the result: "calls to `fdc3.raiseIntent` should not return an `IntentResolution` until the intent handler has been added and the intent delivered to the target app." — [API Overview 3.0](https://fdc3.finos.org/docs/api/spec)
- **CONFIRMED.** 15-second rule: agents MUST "Allow, by default, at least a 15 second timeout" for a launched app to add listeners; handlers "SHOULD be registered via `fdc3.addIntentListener` within 15 seconds of the application launch"; agents "MAY support longer timeouts". No deadline is given for how long a handler may take to produce its result — [API Overview 3.0](https://fdc3.finos.org/docs/api/spec)
- **NEW.** One handler per intent: a second `addIntentListener` for the same intent "MUST" be rejected with `ResolveError.IntentListenerConflict` (3.0 allows several if filtered to non-overlapping context types). Note: this constant is cited in the spec text but does not appear in the enumeration printed on the Errors page as fetched — [API Overview 3.0](https://fdc3.finos.org/docs/api/spec), [Errors 3.0](https://fdc3.finos.org/docs/api/ref/Errors)

Resolver UI
- **CONFIRMED.** Agents MUST "Provide a method of resolving ambiguous intents (i.e. those that might be resolved by multiple applications) or unspecified intents (calls to `raiseIntentForContext` that return multiple options), such as a resolver UI." — [API Overview 3.0](https://fdc3.finos.org/docs/api/spec)
- **CONFIRMED.** "Where the target application is ambiguous (because there is more than one application that could resolve the intent and context) Desktop Agents may resolve intents by any suitable methodology. A common method is to display a UI that allows the user to pick the desired App from a list of those that will accept the intent and context. Alternatively, the app issuing the intent may proactively handle resolution by calling `findIntent` or `findIntentsByContext` and then raise the intent with a specific target application" — [API Overview 3.0](https://fdc3.finos.org/docs/api/spec)
- **NEW.** The chooser is skipped when unambiguous: the promise resolves when the "Intent was resolved unambiguously and the receiving app was launched successfully (if necessary)" or when "Intent was ambiguous, a resolution was chosen by the end user, and the chosen application was launched successfully." — [API Overview 3.0](https://fdc3.finos.org/docs/api/spec)
- **NEW.** The spec gives no layout, ordering or "remember my choice" rule: "UX of application resolution" is listed among areas "not currently areas considered for standardization under FDC3" — [API Overview 3.0](https://fdc3.finos.org/docs/api/spec)

What the Desktop Agent must not do to messages
- **NEW.** "Desktop Agents MUST NOT modify or strip `signature` or `antiReplay` fields." And: "Desktop Agents MUST forward both fields unchanged from the sender's `AppProvidableContextMetadata` to the receiving application's handler — they MUST NOT inspect, strip, or modify them. Cryptographic verification is the sole responsibility of the receiving application, not the Desktop Agent." — [API Overview 3.0](https://fdc3.finos.org/docs/api/spec)
- **NEW.** App-provided metadata (`traceId`, `signature`, `antiReplay`, `custom`): "The Desktop Agent MUST forward these fields unchanged to the handler." — [API Overview 3.0](https://fdc3.finos.org/docs/api/spec)
- **NEW.** The agent owns two fields and ignores app attempts to set them: "Apps SHOULD NOT provide timestamps; if they do, the Desktop Agent MUST ignore them." "Apps SHOULD NOT provide `source`; if they do, the Desktop Agent MUST ignore it." — [API Overview 3.0](https://fdc3.finos.org/docs/api/spec)
- **NEW.** Correlation: "the Desktop Agent MUST forward a `traceId` supplied by the originating application unchanged, and MUST generate a `traceId` when the originating application did not supply one, so that a `traceId` is always present." "Apps MAY propagate `traceId` when performing actions as a result of another FDC3 action. This supports observability and correlation across workflows." — [API Overview 3.0](https://fdc3.finos.org/docs/api/spec)
- **NEW.** No echo: agents SHOULD "Ensure that context messages broadcast by an application on a channel are not delivered back to that same application if they are joined to the channel." — [API Overview 3.0](https://fdc3.finos.org/docs/api/spec)
- **CORRECTED (partly).** The earlier notes said origin metadata is optional and receivers must cope with its absence. 3.0 still says "Metadata is optional and SHOULD be provided by the Desktop Agent to registered listeners, but apps MUST handle cases where it is absent", but the same page also says "Registered listeners MUST receive: `timestamp`, `source`, `traceId`" and lists making this metadata available under MUST. The 3.0 text is internally inconsistent on this point; the stronger reading (always present) is the newer one. `ContextMetadata.source` by name is now confirmed — [API Overview 3.0](https://fdc3.finos.org/docs/api/spec), [Types reference 3.0](https://fdc3.finos.org/docs/api/ref/Types)
- **NEW.** Separation of payload and envelope: "FDC3 separates Context (business data) from ContextMetadata (delivery and provenance information) to maintain clarity and interoperability." Handlers "receive two arguments: `Context` and `ContextMetadata`" — [API Overview 3.0](https://fdc3.finos.org/docs/api/spec)

Channels
- **NEW (exact definition).** "Context channels allows a set of apps to share a stateful piece of data between them, and be alerted when it changes." Three types: User channels ("created and named by the desktop agent", discoverable, joinable, one at a time), App channels ("created and named by applications", "not discoverable"), Private channels ("facilitate private communication between two parties", "can only be retrieved via a raised intent") — [API Overview 3.0](https://fdc3.finos.org/docs/api/spec)
- **NEW.** Channels hold state: "a channel retains the most recent context object of each type that has been broadcast to it, along with the associated `ContextMetadata`", so a late joiner gets current context without a new broadcast — [API Overview 3.0](https://fdc3.finos.org/docs/api/spec)
- **NEW.** "Joining channels in FDC3 is intended to be a behavior initiated by the end user." "There SHOULD always be a clear UX indicator of what channel an app is joined to." — [API Overview 3.0](https://fdc3.finos.org/docs/api/spec)
- **NEW.** One-to-one alternative to broadcast: "For single transactions, this can instead be implemented via a raised intent, which will be delivered to a single application that can, optionally, respond with data." — [API Overview 3.0](https://fdc3.finos.org/docs/api/spec)

App Directory (the capability registry)
- **NEW (exact definition).** "An application directory (appD) is a structured repository of information about apps that can be used in an FDC3-enabled desktop." It serves two readers, "the Desktop Agent" and "humans", so holds "both unique identifiers for apps that are used to refer to them in code and human-friendly app names, icons, descriptions and tooltips necessary to populate a launcher menu or app catalog" — [App Directory Overview 3.0](https://fdc3.finos.org/docs/app-directory/overview)
- **NEW.** "if an app is not listed in appD, the Desktop Agent can't ensure its participation in context sharing or use it to resolve intents." — [App Directory Overview 3.0](https://fdc3.finos.org/docs/app-directory/overview)
- **CONFIRMED.** Capability declaration: records carry an optional `interop` field that declares "what intents the app listens for (`interop.intents.listensFor`) and raises (`interop.intents.raises`)" plus `interop.userChannels` and `interop.appChannels`. "Applications only need to complete the elements of the `interop` element that they make use of." — [App Directory Overview 3.0](https://fdc3.finos.org/docs/app-directory/overview)
- **CONFIRMED.** "Typically, this SHOULD be done via registration with an App Directory by providing `interop.intents.listensFor` metadata. However, Desktop Agent implementations MAY support dynamic registration of an `IntentHandler` by an app at runtime ... which may be helpful at development time." — [API Overview 3.0](https://fdc3.finos.org/docs/api/spec)
- **NEW.** The directory API is two read-only endpoints: `/v2/apps` (GET, all definitions) and `/v2/apps/{appId}` (GET) — [App Directory API 3.0](https://fdc3.finos.org/docs/app-directory/spec)

Error enumerations (3.0, exact string values)
- **NEW.** General rule: "Errors MUST be returned by rejecting the promise returned by the API with a JavaScript `Error` object... The `Error` Object's message should be chosen from the appropriate Error enumeration" — [Errors 3.0](https://fdc3.finos.org/docs/api/ref/Errors)
- **CONFIRMED with additions.** `ResolveError`: `NoAppsFound`; `ResolverUnavailable`; `UserCancelled = "UserCancelledResolution"` ("Returned if the user cancelled the resolution request, for example by closing or cancelling a resolver UI"); `ResolverTimeout` ("SHOULD be returned if a timeout cancels an intent resolution that required user interaction"); `TargetAppUnavailable`; `TargetInstanceUnavailable` ("for example because it has been closed"); `IntentDeliveryFailed` ("for example because it has not added an intent handler within a timeout"); `MalformedContext`; `DesktopAgentNotFound` (experimental); `ApiTimeout`; `InvalidArguments`. Earlier notes omitted `ResolverUnavailable`, `DesktopAgentNotFound`, `InvalidArguments` and the literal string for `UserCancelled` — [Errors 3.0](https://fdc3.finos.org/docs/api/ref/Errors)
- **CONFIRMED.** `ResultError`: `NoResultReturned` ("Returned if the intent handler exited without returning a valid result (a promise resolving to a Context, Channel object or void)"); `IntentHandlerRejected` ("throws an error or rejects the Promise it returned"); `ApiTimeout` ("Returned if a timeout occurs before the getResult() API call is resolved") — [Errors 3.0](https://fdc3.finos.org/docs/api/ref/Errors)
- **NEW.** `OpenError`: `AppNotFound`, `ErrorOnLaunch`, `AppTimeout`, `ResolverUnavailable`, `MalformedContext`, `DesktopAgentNotFound`, `ApiTimeout`, `InvalidArguments`. `ChannelError`: `NoChannelFound`, `AccessDenied`, `CreationFailed`, `MalformedContext`, `ApiTimeout`, `InvalidArguments`. `CloseError`: `ErrorOnClose`, `ApiTimeout`. `AgentError`: `AgentNotFound`, `AccessDenied`, `ErrorOnConnect`, `InvalidFailover`, `ApiTimeout`. A `BridgingError` enumeration also exists (out of scope) — [Errors 3.0](https://fdc3.finos.org/docs/api/ref/Errors)

### Inferences
- Mindstream's design is closest to FDC3's "Client-Service" intent model for ASK and "Chain" for SEND; FDC3 itself says Chain is "the primary focus", so ASK is the less-trodden path even in the standard Mindstream drew on.
- FDC3 3.0's envelope is the direct precedent for a Mindstream message header: broker-stamped `source` and `timestamp` (tools cannot forge them), and a `traceId` that the broker generates if missing and never alters. Mindstream's correlation id is the same idea.
- The "MUST NOT inspect, strip, or modify" rule is the nearest thing in any source read to a written "dumb broker" requirement. For Mindstream the equivalent rule would be: the broker may add header fields but never reads or rewrites the text or the prompt list.
- FDC3's `Stateless` characteristic ("Workflows should not require callbacks or endpoints to maintain references to each other") supports the decision that tools never reference each other.
- Context's single required field, `type`, used only for routing, suggests Mindstream's two shapes (text, prompt list) need nothing more than a type tag for the registry to match on.
- FDC3 has no shelf or holding area concept; a channel's retained "most recent context of each type" is the only stored-in-transit state, and it is overwrite-on-write, not a queue.

### Gaps
- The resolver UI's look, ordering and any "remember my choice" behaviour are explicitly unstandardised; vendor documentation (Here/OpenFin, io.Connect) was out of scope for this pass and remains **STILL UNVERIFIED**.
- Individual intent pages (for example StartChat) and individual context schema pages were not opened; only the lists were read.
- AppD `resultType` field name was not confirmed in the overview page text (the OpenAPI schema was not opened). **STILL UNVERIFIED.**
- `ResolveError.IntentListenerConflict` is referenced in spec prose but absent from the Errors page enumeration as fetched; this may be a documentation lag in 3.0.
- Events, PrivateChannel, GetAgent, Security & Identity and Agent Bridging pages were not read.

## 2. VS Code extension API (code.visualstudio.com/api)

### Takeaway
The earlier notes' description of VS Code is confirmed in every particular, and the missing pieces are now sourced: `executeCommand<T>` returns a `Thenable<T>` so commands are a request-and-return mechanism, menu ordering uses `group@order` with `navigation` first, and the docs state outright that extensions are isolated from the UI and loaded lazily so that a misbehaving extension cannot hurt the editor.

### Cited Findings
All pages below are stamped 11/18/2026.

The three concepts
- **NEW (exact definitions).** "Activation Events: events upon which your extension becomes active." "Contribution Points: static declarations that you make in the `package.json` Extension Manifest to extend VS Code." "VS Code API: a set of JavaScript APIs that you can invoke in your extension code." — [Extension Anatomy](https://code.visualstudio.com/api/get-started/extension-anatomy)
- **NEW.** "Contribution Points are a set of JSON declarations that you make in the `contributes` field of the `package.json` Extension Manifest." The list as of this date has 41 entries, including `commands`, `menus`, `submenus`, `keybindings`, `views`, `viewsContainers`, `configuration`, `customEditors`, `languageModelTools` — [Contribution Points](https://code.visualstudio.com/api/references/contribution-points)

Isolation and lazy activation
- **NEW.** "VS Code aims to deliver a stable and high performance editor to users, and misbehaving extensions should not impact the user experience. The Extension Host in VS Code prevents extensions from: Impacting startup performance / Slowing down UI operations / Modifying the UI" — [Extension Host](https://code.visualstudio.com/api/advanced-topics/extension-host)
- **NEW.** "Additionally, VS Code lets extensions declare their Activation Events and loads them lazily. For example, the Markdown extension should only be loaded when a user opens a Markdown file. This makes sure that extensions do not consume unnecessary CPU and memory." — [Extension Host](https://code.visualstudio.com/api/advanced-topics/extension-host)
- **NEW.** "we also impose restrictions upon extensions to ensure the stability and performance of VS Code. For example, extensions cannot access the DOM of VS Code UI." And: "To ensure that extensions cannot interfere with the stability and performance of VS Code, and that we can continue to improve the DOM of VS Code without breaking existing extensions, we run extensions in an Extension Host process and prevent direct access to the DOM." — [Extension Capabilities Overview](https://code.visualstudio.com/api/extension-capabilities/overview)
- **NEW.** "It is best practice to activate only when a user needs your extension." On the `*` (start-up) event: "To ensure a great user experience, please use this activation event in your extension only when no other activation events combination works in your use-case." `onStartupFinished` "is similar to the `*` activation event, but it will not slow down VS Code startup." — [Activation Events](https://code.visualstudio.com/api/references/activation-events)
- **NEW.** Activation events available (list as of this date): onAuthenticationRequest, onChatParticipant, onCommand, onCustomEditor, onDebug (and four sub-events), onEditSession, onFileSystem, onIssueReporterOpened, onLanguage, onLanguageModelTool, onNotebook, onOpenExternalUri, onRenderer, onSearch, onStartupFinished, onTaskType, onTerminal (and two sub-events), onUri, onView, onWalkthrough, onWebviewPanel, workspaceContains, `*` — [Activation Events](https://code.visualstudio.com/api/references/activation-events)

Commands, including return values
- **NEW.** "In short, a command is a function with a unique identifier." `registerCommand(command: string, callback: (args: any[]) => any, thisArg?: any): Disposable`; "Registering a command with an existing command identifier twice will cause an error." `executeCommand<T>(command: string, ...rest: any[]): Thenable<T>` — [VS Code API reference](https://code.visualstudio.com/api/references/vscode-api) (API reference page stamped 02/04/2026)
- **CORRECTED from "not sourced" to CONFIRMED.** "Some commands take arguments that control their behavior. Commands may also return a result. The API-like `vscode.executeDefinitionProvider` command, for example, queries a document for definitions at a given position. It takes a document URI and a position as arguments, and returns a promise with a list of definitions" — [Command guide](https://code.visualstudio.com/api/extension-guides/command)
- **NEW.** Commands are the cross-extension interface: "Many extensions also expose their core functionality as commands that users and other extensions can leverage." An `onCommand` event (pre-1.74) was required for any command that "Is intended as an API for other extensions to consume." — [Command guide](https://code.visualstudio.com/api/extension-guides/command)
- **NEW.** One handler, many entry points: "The handler function will be invoked whenever the `myExtension.sayHello` command is executed, be it programmatically with `executeCommand`, from the VS Code UI, or through a keybinding." The arguments differ by entry point (a table gives: `executeCommand` passes the args given; Command Palette passes "No arguments"; a menu item passes "Context supplied by the menu, such as a document URI or selected resources"). "If you expose a command in both a resource menu and the Command Palette, handle calls without a resource argument." — [Command guide](https://code.visualstudio.com/api/extension-guides/command)
- **NEW.** Declaration is separate from registration: "`vscode.commands.registerCommand` only binds a command ID to a handler function. To expose this command in the Command Palette so it is discoverable by users, you also need a corresponding command `contribution` in your extension's `package.json`" — [Command guide](https://code.visualstudio.com/api/extension-guides/command)
- **CONFIRMED.** "When a command is invoked (from a key binding, from the Command Palette, any other menu, or programmatically), VS Code will emit an activationEvent `onCommand:${command}`." — [Contribution Points](https://code.visualstudio.com/api/references/contribution-points)
- **CONFIRMED.** "Beginning with VS Code 1.74.0, commands contributed by your extension do not require a corresponding `onCommand` activation event declaration for your extension to be activated." — [Activation Events](https://code.visualstudio.com/api/references/activation-events)
- **NEW.** Command URIs: "Commands URIs are links that execute a given command." Form `command:editor.action.addCommentLine`; "The list of arguments to the command is passed as a JSON array that has been properly URI encoded" — [Command guide](https://code.visualstudio.com/api/extension-guides/command)

`when` clause contexts
- **CONFIRMED.** "Visual Studio Code sets various context keys and specific values depending on what elements are visible and active in the VS Code UI. These contexts can be used to selectively enable or disable extension commands and UI elements, such as menus and views." — [when clause contexts](https://code.visualstudio.com/api/references/when-clause-contexts)
- **NEW.** Operators documented: logical, equality, comparison, a regex match operator (`=~`), and `in` / `not in` ("allows for a dynamic lookup of a context key's value within another context key's value"). Extensions add their own keys with `vscode.commands.executeCommand('setContext', 'ext.supportedFolders', [...])` — [when clause contexts](https://code.visualstudio.com/api/references/when-clause-contexts)
- **NEW.** "A `when` clause controls whether a menu item is visible. It does not pass its context keys to the command handler." — [Command guide](https://code.visualstudio.com/api/extension-guides/command)

Menus
- **CONFIRMED.** "Contribute a menu item for a command to the editor or Explorer. ## 6. Martin Fowler's site: "smart endpoints and dumb pipes" and "Tolerant Reader"

### Takeaway
Both earlier second-hand quotations are confirmed word for word in the original article (James Lewis and Martin Fowler, "Microservices", 25 March 2014). The "Tolerant Reader" bliki entry (Fowler, 9 May 2011) exists and gives a directly usable rule for message consumers: take only what you need and ignore the rest.

### Cited Findings
- **CONFIRMED (exact).** "The microservice community favours an alternative approach: smart endpoints and dumb pipes. Applications built from microservices aim to be as decoupled and as cohesive as possible - they own their own domain logic and act more as filters in the classical Unix sense - receiving a request, applying logic as appropriate and producing a response. These are choreographed using simple RESTish protocols rather than complex protocols such as WS-Choreography or BPEL or orchestration by a central tool." — [Lewis and Fowler, Microservices](https://martinfowler.com/articles/microservices.html)
- **CONFIRMED (exact).** What they oppose: "When building communication structures between different processes, we've seen many products and approaches that stress putting significant smarts into the communication mechanism itself. A good example of this is the Enterprise Service Bus (ESB), where ESB products often include sophisticated facilities for message routing, choreography, transformation, and applying business rules." — [Lewis and Fowler, Microservices](https://martinfowler.com/articles/microservices.html)
- **CONFIRMED (exact).** "The second approach in common use is messaging over a lightweight message bus. The infrastructure chosen is typically dumb (dumb as in acts as a message router only) - simple implementations such as RabbitMQ or ZeroMQ don't do much more than provide a reliable asynchronous fabric - the smarts still live in the end points that are producing and consuming messages; in the services." — [Lewis and Fowler, Microservices](https://martinfowler.com/articles/microservices.html)
- **NEW.** Granularity warning relevant to in-process tools: "In a monolith, the components are executing in-process and communication between them is via either method invocation or function call... A naive conversion from in-memory method calls to RPC leads to chatty communications which don't perform well. Instead you need to replace the fine-grained communication with a coarser -grained approach." — [Lewis and Fowler, Microservices](https://martinfowler.com/articles/microservices.html)
- **NEW.** On versioning: "the preference in the microservice world is to only use versioning as a last resort. We can avoid a lot of versioning by designing services to be as tolerant as possible to changes in their suppliers." And: "Patterns like Tolerant Reader and Consumer-Driven Contracts are often applied to microservices. These aid service contracts in evolving independently." — [Lewis and Fowler, Microservices](https://martinfowler.com/articles/microservices.html)
- **NEW.** Attribution: the article is by James Lewis and Martin Fowler (in that order), dated 25 March 2014. The earlier notes wrote "Fowler and Lewis" — [Lewis and Fowler, Microservices](https://martinfowler.com/articles/microservices.html)
- **NEW.** Tolerant Reader (Martin Fowler, 9 May 2011): "The governing law for decoupled collaboration should be Postel's Law: be conservative in what you do, be liberal in what you accept from others." — [Fowler, Tolerant Reader](https://martinfowler.com/bliki/TolerantReader.html)
- **NEW.** "My recommendation is to be as tolerant as possible when reading data from a service. If you're consuming an XML file, then only take the elements you need, ignore anything you don't. Furthermore make the minimum assumptions about the structure of the XML you're consuming." "Your aim should be to allow the provider to make any change that ought not to break your code." — [Fowler, Tolerant Reader](https://martinfowler.com/bliki/TolerantReader.html)
- **NEW.** "On top of this, make sure there's only one bit of code that reads data payloads like this." — [Fowler, Tolerant Reader](https://martinfowler.com/bliki/TolerantReader.html)
- **NEW.** "Adding field to an interface like this shouldn't be a breaking change for anyone - but often does break these schemes." And a practical tip: put data "into generic collections (lists and maps)" so that "If you add an extra field to a map, it will still deserialize on the other side and it's easy for a tolerant reader to ignore it." — [Fowler, Tolerant Reader](https://martinfowler.com/bliki/TolerantReader.html)

### Inferences
- The Lewis and Fowler list of what makes a pipe "smart" (routing, choreography, transformation, business rules) is a usable checklist of what Mindstream's broker must not acquire. A routing slip carried on the message keeps choreography out of the pipe.
- Their description of endpoints as "filters in the classical Unix sense - receiving a request, applying logic as appropriate and producing a response" is the ASK contract in one line.
- Tolerant Reader applied to Mindstream: each tool should read only the envelope fields it uses and ignore unknown ones, and each tool should have a single function that unpacks an incoming message. That allows the envelope to grow (provenance, a third shape) without touching every tool.
- The article is about networked services; applying it to tools inside one browser page is an analogy, though the authors' own warning about chatty fine-grained calls supports Mindstream's coarse "text plus prompt list" messages.

Mindstream's design is a textbook combination of Routing Slip, Request-Reply, Return Address and Correlation Identifier over a Canonical Data Model of two shapes, with Document Message for SEND and Command Message for ASK, and it deliberately avoids Content-Based Router, Message Translator and Process Manager.

### Cited Findings
Each page gives a problem statement, a one-sentence solution, and a few paragraphs, then "... Read the entire pattern in the book Enterprise Integration Patterns". The pages carry no date.

- **NEW (exact).** Routing Slip. Problem: "How do we route a message consecutively through a series of processing steps when the sequence of steps is not known at design-time and may vary for each message?" Solution: "Attach a Routing Slip to each message, specifying the sequence of processing steps. Wrap each component with a special message router that reads the Routing Slip and routes the message to the next component in the list." Mechanics: "We insert a special component into the beginning of the process that computes the list of required steps for each message. It then attaches the list as a Routing Slip to the message and starts the process by routing the message to the first processing step. After successful processing, each processing step looks at the Routing Slip and passes the message to the next processing step specified in the routing table." Note the page's file name is `RoutingTable.html` — [Routing Slip](https://www.enterpriseintegrationpatterns.com/patterns/messaging/RoutingTable.html)
- **NEW (exact).** Routing Slip's stated limits, from the Process Manager page: "The solution of the Routing Slip is based on two key assumptions: the sequence of processing steps has to be determined up-front and the sequence is linear. In many cases, these assumptions may not be fulfilled. For example, routing decisions might have to be made based on intermediate results. Or, the processing steps may not be sequential, but multiple steps might be executed in parallel." — [Process Manager](https://www.enterpriseintegrationpatterns.com/patterns/messaging/ProcessManager.html)
- **NEW (exact).** Process Manager (the alternative Mindstream is not choosing): "Use a central processing unit, a Process Manager, to maintain the state of the sequence and determine the next processing step based on intermediate results." It produces "a so-called hub-and-spoke pattern of message flow", and the authors warn: "We think that using a Process Manager for every situation may be overkill. It can distract from the core design issue and also cause significant performance overhead." — [Process Manager](https://www.enterpriseintegrationpatterns.com/patterns/messaging/ProcessManager.html)
- **NEW (exact).** Document Message. "How can messaging be used to transfer data between applications?" "Use a Document Message to reliably transfer a data structure between applications." "Whereas a Command Message tells the receiver to invoke certain behavior, a Document Message just passes data and lets the receiver decide what, if anything, to do with the data." — [Document Message](https://www.enterpriseintegrationpatterns.com/patterns/messaging/DocumentMessage.html)
- **NEW (exact).** Command Message. "How can messaging be used to invoke a procedure in another application?" "Use a Command Message to reliably invoke a procedure in another application." "There is no specific message type for commands; a Command Message is simply a regular message that happens to contain a command." — [Command Message](https://www.enterpriseintegrationpatterns.com/patterns/messaging/CommandMessage.html)
- **NEW (exact).** Message Translator. "How can systems using different data formats communicate with each other using messaging?" "Use a special filter, a Message Translator, between other filters or applications to translate one data format into another." "The Message Translator is the messaging equivalent of the Adapter pattern described in [GoF]." — [Message Translator](https://www.enterpriseintegrationpatterns.com/patterns/messaging/MessageTranslator.html)
- **NEW (exact).** Canonical Data Model. "How can you minimize dependencies when integrating applications that use different data formats?" "Therefore, design a Canonical Data Model that is independent from any specific application. Require each application to produce and consume messages in this common format." Cost note: "The use a Canonical Data Model seems complicated if only a small number of applications participate in the integration solution... a solution consisting of 2 applications would require only 2 Message Translators if we translate between the applications' data formats directly whereas the Canonical Data Model requires 4 Message Translators. A solution consisting of 3 applications requires 6 Message Translators with either approach. However, a solution consisting of 6 applications requires 30(!) Message Translators without a Canonical Data Model and only 12 Message Translators when using a Canonical Data Model." — [Canonical Data Model](https://www.enterpriseintegrationpatterns.com/patterns/messaging/CanonicalDataModel.html)
- **NEW (exact).** Content-Based Router. "Use a Content-Based Router to route each message to the correct recipient based on message content." Warning: "special caution should be taken to make the routing function easy to maintain as the router can become a point of frequent maintenance." — [Content-Based Router](https://www.enterpriseintegrationpatterns.com/patterns/messaging/ContentBasedRouter.html)
- **NEW (exact).** Request-Reply. "When an application sends a message, how can it get a response from the receiver?" "Send a pair of Request-Reply messages, each on its own channel." Participants: "Requestor – Sends a request message and waits for a reply message." "Replier – Receives the request message and responds with a reply message." "The reply channel, on the other hand, is almost always point-to-point, because it usually makes no sense to broadcast replies–they should only be returned to the requestor." — [Request-Reply](https://www.enterpriseintegrationpatterns.com/patterns/messaging/RequestReply.html)
- **NEW (exact).** Request-Reply, two ways to wait. "Synchronous Block" is "simple to implement, but if the requestor crashes, it will have difficulty re-establishing the blocked thread." "Asynchronous Callback": "When a reply message arrives, the reply thread invokes the appropriate callback, which re-establishes the caller's context and processes the reply... If the requestor crashes, it can recover by simply restarting the reply thread. An added complexity, however, is the callback mechanism that must re-establish the caller's context." — [Request-Reply](https://www.enterpriseintegrationpatterns.com/patterns/messaging/RequestReply.html)
- **NEW (exact).** Correlation Identifier. "How does a requestor that has received a reply know which request this is the reply for?" "Each reply message should contain a Correlation Identifier, a unique identifier that indicates which request message this reply is for." Six parts, including "Request ID — A token in the request that uniquely identifies the request" and "Correlation ID — A token in the reply that has the same value as the request ID in the request"; the replier "gets the request ID from the request and stores it as the correlation ID in the reply." — [Correlation Identifier](https://www.enterpriseintegrationpatterns.com/patterns/messaging/CorrelationIdentifier.html)
- **NEW (exact).** Return Address. "How does a replier know where to send the reply?" "The request message should contain a Return Address that indicates where to send the reply message." "This way, the replier does not need to know where to send the reply, it can just ask the request... This encapsulates the knowledge of what channels to use for requests and replies within the requestor so those decisions do not have to be hard coded within the replier. A Return Address is put in the header of a message because it's not part of the data being transmitted." — [Return Address](https://www.enterpriseintegrationpatterns.com/patterns/messaging/ReturnAddress.html)

### Inferences
Mapping of Mindstream's decisions to the patterns:
- "Steps carried on the message, like a routing slip" = **Routing Slip**, exact match. Consequence the pattern states: each tool (or a thin wrapper round it) must read the slip and forward to the next step; the broker does not decide. The pattern's two stated assumptions also become Mindstream's limits: the prompt list is fixed when the message is created, and it is linear. If Mindstream ever wants "choose the next step from the previous answer" or parallel steps, the authors say that is Process Manager territory, which means state in the hub and the end of the dumb broker.
- "ASK: send text and get a result back at the origin" = **Request-Reply**, using the **Asynchronous Callback** variant. The pattern's own caveat ("the callback mechanism that must re-establish the caller's context") is the same issue the earlier notes drew from Android: the origin tool needs enough saved context to place the answer after a reload.
- "Reply address on the message" = **Return Address**, exact match, including the detail that it belongs in the header, not the payload. This is what lets tools "never reference each other".
- "Correlation id on the message" = **Correlation Identifier**, exact match. The pattern separates the request id from the correlation id copied into the reply; a single field reused in both directions is the usual simplification.
- "SEND (one-way)" = **Document Message**: pass data and let the receiver decide what to do.
- "ASK" = closer to **Command Message** (a request to do something), with the prompt list as the command.
- "Messages carry only text and an ordered list of prompts" = a two-shape **Canonical Data Model**. The page's own arithmetic says a canonical model does not pay for itself at 2 participants and breaks even at 3; with only two shapes and all tools first-party, the cost is negligible, so this is not a reason to change course.
- Patterns deliberately not used: **Content-Based Router** (the user picks via Send-to; the site warns such routers become "a point of frequent maintenance"), **Message Translator** (no per-tool formats), **Process Manager** (no central workflow state).
- Routing Slip plus Return Address interact: the Routing Slip page lists Return Address as a related pattern. For an ASK that travels through several steps, the reply address must survive every hop unchanged, which argues for the broker treating header fields as opaque.

### Gaps
- Only the web summaries were read; the full pattern text (forces, variants, worked examples) is in the book and remains **STILL UNVERIFIED**. In particular, the Routing Slip chapter's discussion of where the slip logic lives (in each component versus in a wrapper) is not on the web page beyond the single sentence quoted.
- Message Broker, Envelope Wrapper, Message History and Claim Check pages (all plausibly relevant to a shelf or to provenance) were not opened.

## 8. Plan 9 plumber (9p.io): Pike, "Plumbing and Other Utilities"

### Takeaway
The paper was read in full at 9p.io. It confirms the earlier notes (first matching rule set wins, send file and named ports, fan-out to several readers) and settles the items left unverified: plumbing has "no concept of a reply to a message", a failed match is reported to the sender as a write error, delivery is deliberately non-blocking and not guaranteed, and a non-running target is started by `plumb start` or `plumb client` rules. Unlike Mindstream's broker, the plumber is not dumb: it rewrites messages.

### Cited Findings
The paper as served at 9p.io is undated (it was presented at USENIX 2000).

- **CONFIRMED (exact).** "The core of the plumbing system is a program called the plumber, which handles all messages and dispatches and reformats them according to configuration rules written in a special-purpose language. This approach allows the contents and context of a piece of data to define how it is handled. Unlike with drag and drop or cut and paste, the user doesn't need to deliver the data; the contents of a plumbing message, as interpreted by the plumbing rules, determine its destination." — [Pike, Plumbing and Other Utilities](https://9p.io/sys/doc/plumb.html)
- **NEW (exact).** Motivation: "Why should a human do the work? Usually there is one obvious thing to do with a piece of data, and the data itself suggests what this is." "We want a system that, given a piece of data, hands it to the appropriate application by default with little or no human intervention, while still permitting the user to override the defaults if desired." — [Pike](https://9p.io/sys/doc/plumb.html)
- **CONFIRMED.** Mechanism: "programs send messages by writing them to the plumber's file `/mnt/plumb/send`, and receive messages by reading them from ports, which are other plumber files in `/mnt/plumb`. For example, `/mnt/plumb/edit` is by convention the file from which a text editor reads messages requesting it to open and display a file for editing." — [Pike](https://9p.io/sys/doc/plumb.html)
- **NEW.** Message format: "a fixed-format textual header followed by a free-format data section. The header consists of six lines of text": the source application, the destination port, the working directory, "The type of the data, analogous to a MIME type, such as text or image/gif", attributes as "name=value pairs", and the length of the data — [Pike](https://9p.io/sys/doc/plumb.html)
- **CONFIRMED.** Rule matching: "The plumber receives the message and applies the plumbing rules successively to it. When a rule set matches, the message is dispatched as indicated by that rule set and processing continues with the next message." — [Pike](https://9p.io/sys/doc/plumb.html)
- **NEW (was unverified).** No match: "If no rule set matches the message, the plumber indicates this by returning a write error to the application, that is, the write to `/mnt/plumb/send` fails, with the resulting error string describing the failure... Thus a program can discover whether a plumbing message has been sent successfully." — [Pike](https://9p.io/sys/doc/plumb.html)
- **NEW.** The plumber rewrites: "After a matching rule set has been identified, the plumber applies a series of rewriting steps to the message... The rule set may contain actions that explicitly rewrite components of the message. These may modify the attribute list or replace the data section of the message." — [Pike](https://9p.io/sys/doc/plumb.html)
- **NEW.** Explicit addressing bypasses rules: "(If it matches no rule sets, but mentions a port, it will be sent there unmodified.)" — [Pike](https://9p.io/sys/doc/plumb.html)
- **CONFIRMED.** Fan-out: "If multiple applications are reading from the destination port, each will receive an identical copy of the message; that is, the plumber implements fan-out." — [Pike](https://9p.io/sys/doc/plumb.html)
- **NEW (was unverified).** One-way and best-effort by design: "this design also means that there is no way for a sender to know when the message has been handled; in fact, there are cases when the message will not be delivered at all, such as if the recipient exits while there are still messages in the queue. Since the plumber is part of a user interface, and not an autonomous message delivery system, the decision was made to give the non-blocking property priority over reliability of message delivery." And, comparing with the FIELD system: "the plumber has no concept of a reply to a message" — [Pike](https://9p.io/sys/doc/plumb.html)
- **NEW (was unverified).** Starting a target: "If the port is not open, a `plumb start` or `plumb client` action will start a new program to handle the message." `plumb start`: "its argument specifies a command to run instead of passing on the message; the message is discarded." `plumb client` "is therefore like plumb start, but keeps the message around for delivery when the application opens the port." — [Pike](https://9p.io/sys/doc/plumb.html)
- **NEW (was unverified).** The Acme gesture: "With a three-button mouse, clicking the right button in Acme on a piece of text tells Acme to get the thing being pointed to." Now, "Acme constructs a plumbing message... It then writes the message to the plumber; if the write succeeds, all is well. If not, it falls back to its original, internal rules" — [Pike](https://9p.io/sys/doc/plumb.html)
- **NEW.** Applications' ignorance of each other and of the plumber: "Most applications work fine in a plumbing environment without knowing about it at all; some need trivial changes such as to standardize their error output; a few need to generate and receive plumbing messages. But even to add the ability to send and receive messages in a program such as text editor is short work, involving typically a few dozen lines of code." "The plumber itself is only about two thousand lines of C code." — [Pike](https://9p.io/sys/doc/plumb.html)
- **NEW.** Same wiring regardless of which tool is on the other end: "Notice how the plumbing connects the components of the interface together the same way regardless of which components are actually being used to view mail." — [Pike](https://9p.io/sys/doc/plumb.html)
- **NEW.** Where the work sits: the architecture "guarantees uniform handling of inter-application messages; it off-loads from those applications most of the work of extracting and dispatching messages". Against Tcl: "Plumbing, on the other hand, provides minimal support within the application, offloading most of the message handling and all the command execution to the central plumber." — [Pike](https://9p.io/sys/doc/plumb.html)
- **NEW.** Pike's own lessons: the first version (for Inferno) "encountered difficulties because the plumber was too disconnected from its clients; in particular, there was no way to discover whether a port was in use." The rewrite means "The plumber now knows whether a port is open, which makes it easy to decide whether a new program must be started to handle a message". Also: "the provision of a central, convenient message-passing service is a good idea regardless of how the programs use it." — [Pike](https://9p.io/sys/doc/plumb.html)
- **NEW.** Stated limitation: "Plumbing's rule language uses only regular expressions and a few special rules such as `isfile` for matching text... the plumbing language has no facility for examining the contents of files named in its messages." — [Pike](https://9p.io/sys/doc/plumb.html)
- **CONFIRMED.** Ports persist: "ports are never deleted dynamically; if a new set of rules does not include a port that was defined in earlier rules, that port will still exist (although no new messages will be delivered there)." Rules are editable live: "appending to this file adds new rules to the set" — [plumber(4)](https://9p.io/magic/man2html/4/plumber)
- **CONFIRMED.** If the port is not open and no start/client rule exists, "the message is discarded and a write error is returned" (sentence truncated in the copy read) — [plumber(4)](https://9p.io/magic/man2html/4/plumber)

### Inferences
- **CORRECTED framing.** The earlier notes called the plumber a "middle position" where "endpoints stay ignorant of each other". That is right about the endpoints, but the plumber is a smart pipe in Lewis and Fowler's sense: it does content-based routing and transformation (rewriting). The intelligence is user-editable rules, but it does live in the middle. Mindstream's broker is dumber than the plumber, with the routing slip and the user's Send-to choice doing the work the plumbing rules do.
- The plumber is a pure SEND system. Its lack of a reply is a stated design choice tied to non-blocking senders, not an oversight. Mindstream's ASK has no precedent here.
- Two plumber mechanics are worth copying regardless: (a) the sender learns synchronously whether the message could be routed at all (delivery failure is immediate, handling is unknowable), and (b) `plumb client`, which holds a message for a target that is not yet running and delivers it when the target opens its port. The second is the same need as delivering to a tool that has not mounted yet, and is a natural job for the shell (or the shelf).
- Pike's Inferno lesson ("no way to discover whether a port was in use") argues that Mindstream's broker, however dumb, must know which tools are currently mounted and listening.
- The six-line header (source, destination, working directory, type, attributes, length) is a minimal envelope precedent: provenance and type in the header, free-form text in the body.

### Gaps
- The paper's sections on the rule language details and the full user-interface section were read only in the passages quoted above, not transcribed in full.
- The plumb(6) man page was fetched but only its `start`/`client` lines were checked.

### Inferences
- Ink and Switch's position is the opposite pole from Mindstream's "tools own their state; only messages cross". Their argument for shared data is about introducing new tools into a workflow with low friction, and about live, synchronised views. Mindstream gets the second of their two sub-problems (a shared workspace where tools are used together) while declining the first (shared data).

Messages carrying plain text and a prompt list sidestep that problem by having almost no schema.
- Potluck's "deferring structured formalism" and "gradual enrichment" are an argument for keeping the message payload as freeform text and letting receiving tools extract structure, rather than adding typed fields to the envelope early.
- The cost Mindstream should watch for is the one Embark names: copies moved between tools lose "the broader context of the task". Provenance in the envelope (origin tool, origin place) is the cheap mitigation; it does not give live linkage.
- The Dynamicland remark ("When a system doesn't assume up front that certain connections exist between senders and receivers") is a point in favour of a broker with a registry over tools holding references to each other.

### Inferences
- Obsidian's model is "host plus plugins that register things", but unlike VS Code and JupyterLab its documented command has no arguments and no return value. It is a palette entry, not an inter-tool call. So Obsidian is a precedent for layout (tree of splits and tabs, leaves typed by view id, a factory per view type) rather than for hand-offs.
- The warning "Never manage references to views... use `getLeavesOfType()`" is the same discipline Mindstream adopted for tools: ask the shell for the current instance by type instead of holding a pointer.
- "Leaves remain after the plugin is disabled" is a restore hazard: a saved layout can reference a tool type that no longer exists. Mindstream's restore should tolerate an unknown tool id by showing a placeholder, not failing.
- `paneType` (replace / tab / split / window) on an incoming request is a compact precedent for letting a Send-to action say where the target should open.
- Obsidian's `x-success` reply returns a reference (name and URI), not content. That is the "send a reference, target looks it up" style FDC3 also describes, and the opposite of Mindstream's "send the text itself".
